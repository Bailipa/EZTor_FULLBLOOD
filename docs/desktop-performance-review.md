## 1. 结论与证据边界

桌面适配存在可从代码确认的结构问题：双端组件同时挂载、桌面导航断点过晚、桌面缺少“我的”入口、首页两列内容不均衡、句子翻译没有桌面对照布局。此前将组件接入现有路由后就视为双端适配完成，完成标准不够充分。

卡顿尚未定位到唯一根因。已经确认重复请求和多余挂载的代码路径，但它们各自造成多少延迟、是否是用户所感到的主要卡顿来源，需要浏览器性能记录进一步量化。不能归咎于电脑性能，也不能只用开发模式解释所有问题。

## 2. 优先改进项

P1：下一轮应优先处理，影响主要入口、重复开销或关键操作。P2：随后处理，需要测量决定优化程度。本次没有足够证据宣称存在 P0 故障。

### P1-01 首页只挂载一份业务内容，去除重复加载

**代码事实：** `src/components/home/HomeContent.tsx:43` 和 `:73` 同时渲染手机和桌面分支，通过 `xl:hidden` / `hidden xl:flex` 控制显示。两份 `HomeHeader` 始终挂载；登录后两份 `DailyTaskCard` 和两份 `CombatPowerBadge` 也同时挂载。CSS 隐藏不会停止 React effect。

`HomeHeader.tsx:29` 和 `CombatPowerBadge.tsx:16` 各自读取 `/api/game/profile`，因此单看这四个实例，就存在四条独立初始请求路径；`DailyTaskCard.tsx:61` 两个实例分别读取任务，并各自监听页面恢复与可见性事件。实际请求次数还受会话加载、开发模式和其他组件影响，本轮未通过 Network 实测次数。

**改进：** 优先使用一份组件树配合响应式布局；学力、任务等同一数据由页面或共用数据层加载一次后传给展示组件。必须不同的双端组件才按断点挂载，避免引入 hydration 闪烁。页面恢复事件合并刷新，并共享在途请求；不能为减少请求而永久显示旧进度。

**验收：** 生产预览稳定登录后，首页初始每类数据仅一次有效加载；切换标签一次不产生两份任务刷新；调整窗口宽度不丢学习状态。记录请求前后计数。

### P1-02 修复隐藏闪卡加载和长度变化触发的重复请求

**代码事实：** 手机分支的 `FullscreenFlashcard` 在桌面也挂载。`src/components/flashcard/FullscreenFlashcard.tsx:60` 的 effect 内调用 `fetchWords()`，依赖数组含 `words.length`。正常加载使长度从 0 变为 20，会再次执行 effect 并请求。长度稳定后不会仅因这个依赖无限循环；应准确称为重复加载风险。

**改进：** 初始加载与恢复监听分开，监听回调通过 ref 或稳定状态读取当前数据；首次加载、bfcache 恢复、标签恢复合并在途请求。桌面不使用的全屏闪卡不启动加载。现有弹窗闪卡 `flashcard-widget.tsx:93` 已在打开弹窗后才加载，保留这一行为，不误改为首页预取全部词条。

**验收：** 从空列表成功加载一次后不因长度变化再请求；桌面首页未打开闪卡时无隐藏全屏闪卡请求；真实 bfcache 恢复仍能获得有效数据，错误后可重试。

### P1-03 拆开翻译初始化依赖，补充任务按需激活

**代码事实：** `src/components/ai/TranslationWorkspace.tsx:49` 将分组和保存偏好放入同一个 `Promise.all`，两者都结束后才展示登录用户的实时面板。分组慢也会阻塞输入区。工作区底部始终挂载 `ZhEnAssistant`，只用 `hidden` 隐藏；后者在 `ZhEnAssistant.tsx:78` 再次请求同一个分组接口。

**改进：** 页面共享分组数据；输入壳立即可见，分组单独显示加载状态。保存偏好未确认时不能因为“加速”就自动保存，应保留输入并等待确认或给出可重试状态。补充面板首次进入时才挂载，其后保留草稿；查询状态与界面挂载分开管理，避免切换时丢输入、重复提交或意外取消已确认保存。

**验收：** 人为延迟分组接口仍能输入；同账号首次进入翻译仅一份分组请求；往返实时/补充任务保留草稿、结果与目标分组；偏好失败不悄悄覆盖用户的手动保存选择。

### P1-04 补齐电脑导航，统一紧凑桌面断点

**代码事实：** `AppSidebar.tsx`、`MobileNavBar.tsx` 和 `AppLayout.tsx` 使用 `xl` 作为两种导航切换点；项目没有覆盖默认 xl 断点，常规根字号下为 1280 CSS px。1024–1279px 的电脑窗口因此只显示手机底栏。默认侧栏列表 `AppSidebar.tsx:46` 缺少 `/me`，而底栏在桌面隐藏，使“我的”设置没有同等直接的主导航入口。

**改进建议：** 小于 768px 使用手机底栏；768–1199px 使用可收起的紧凑侧栏；1200px 以上展开约 224–240px 侧栏。这是下一轮建议值，需要结合主内容可用宽度验证，不能机械替换全站所有 `xl`。主内容偏移、底部安全区和导航一起调整，补上“我的”。键盘焦点和图标侧栏必须有可读名称。

**验收：** 1024、1199、1200、1279、1280、1440px 来回缩放，导航无空档或重叠；桌面一步进入“我的”修改声音/保存设置；200% 缩放仍可操作。按 CSS 视口验收，不按显示器物理分辨率判断设备。

### P1-05 重做桌面首页的信息分配

**代码事实：** `HomeContent.tsx:84` 固定两列比例；左列主要是几颗跳转按钮，右列登录后才有内容，且任务默认收起；游客状态右列仍占位。顶部 `HomeHeader.tsx:53` 使用固定高度、`overflow-hidden` 和不换行的工具栏，空间紧张时存在裁切风险，实际裁切需补截图验证。

**改进：** 首页主区集中呈现“继续学习”，让最近学习上下文与“开始复习”成为主动作；错词本、生词本作为清楚的相邻入口。优先使用现有数据，不为了填满空白新增业务统计。今日进度作为较窄辅助区；游客不保留空列。翻译沿侧栏/底栏进入。顶部移除与侧栏重复的主题、下载等入口，次要工具收进一个菜单，并保证弹窗焦点不受裁切。

**验收：** 1024×768、1280×800、1440×900 的首屏能辨认主要学习动作；游客无空右列；长昵称、浏览器缩放不裁按钮；桌面新手引导仍能定位可见操作。

### P1-06 翻译页采用适合桌面的任务布局

**代码事实：** 工作区限制为 `max-w-5xl`，并有整行双按钮模式切换；`ZhEnAssistant.tsx:266` 的句子输入与结果始终上下堆叠，没有桌面对照布局。实时面板还重复展示“实时翻译”标题（`WordTranslationPanel.tsx:255`）。补充任务又有一层切换，页面顶部占用和层级增加。

**改进：** 保留两条业务入口：实时翻译、补充翻译；第二入口内部提供“找英文 / 译句子”。主切换缩为紧凑工具栏，标题只保留一次。桌面主内容建议最大约 1200px，留 24–32px 边距；句子任务在可用宽度足够时原文/译文左右等宽，窄屏上下排列。实时查词使用统一行布局，中文候选保持便于比较的单列，不为宽屏强拆成多列卡片。

**验收：** 1440px 桌面能同时看原文和译文；1024px 收窄后无横向滚动；手机主按钮和键盘不互相遮挡。主界面不增加“免费”“剩余次数”“不消耗额度”等提示。

### P1-07 统一滚动容器，减少候选操作层级

**代码事实：** `/ai/page.tsx:12` 固定视口高度，`TranslationWorkspace.tsx:108` 的 main 使用 `overflow-hidden`，实时 section 自行滚动；补充任务内部再次定义滚动区域，句子 textarea 自身也可滚动/拉伸。并非这些容器在所有模式都同时产生滚动条，但不同任务由不同容器负责滚动，需逐一确认。中文候选须展开后才出现分组和加入按钮（`ZhEnAssistant.tsx:417`），每个展开项重复分组控件和已展示释义。

**改进：** 普通翻译模式使用一个明确的主滚动区域，避免页面高度与多层溢出裁切叠加；聊天类界面如需独立滚动，单独说明边界。目标生词本提升为共用工具栏；每条候选直接提供“加入”，发音/释义一层可见，更多详情按需展开；当前行显示保存进度，不让一个共享 `adding` 状态把所有候选显示为忙碌。无结果时提供贴近原输入的下一步，不能只把用户送到空白问答页。

**验收：** 鼠标滚轮/触控板从页头到结果连续滚动；聚焦输入、放大文本、切换任务后不跳回错误位置；选定候选后一步保存，失败可原位重试；带回实时仍只预填，不自动生成、保存或计贡献。

## 3. 待测量后优化的项目

### P2-01 多词输入的渲染范围

`useRealtimeTranslation.ts:146` 每次改词更新 entries 数组；`WordTranslationPanel.tsx:307` 渲染所有行，`WordInputRow.tsx:132` 未使用 memo。存在输入一行导致父级重新渲染全部行的路径，具体成本尚未测得。CSV 单次最多 50 词，不应先引入复杂虚拟列表。

先用 1 / 20 / 50 行进行 React Profiler 对比；稳定回调和不变行引用后按需 memo，减少无关行提交。只有较大列表确实成为瓶颈时才分页或虚拟化，保留焦点、IME、键盘连续输入和保存状态。

### P2-02 首屏脚本与次要工具

首页静态导入游戏、弹窗、闪卡等模块链；翻译页静态导入补充组件及问答组件。静态导入不等于所有弹窗 DOM 都挂载，也不能从源码直接得出最终包大小。按生产构建分析模块归属，再对实际较重、低频打开的工具按需加载。避免在体验修复中顺便重写全应用状态管理。

参考项目随包文档：`node_modules/next/dist/docs/01-app/02-guides/production-checklist.md`、`lazy-loading.md`。正式性能对比应使用生产预览，开发编译时间单独列出。

### P2-03 辉金与弹幕的绘制成本

`globals.css:294` 起给金色主按钮和所有 card 叠加多层辉光；`DanmakuHost` 根据开关挂载弹幕，弹幕组件存在刷新/清理定时器。当前用户启用何种主题、弹幕数量和具体绘制成本未核验，不能认定辉光就是卡顿根因。CSS 隐藏元素通常不绘制，重复挂载问题主要针对脚本和副作用，不能混写成“隐藏两套页面持续重绘”。

按紫色/白金/黑金、弹幕开/关记录同操作性能。保留用户明确要求的浓郁辉光；优先减少重复表面与大面积动态重绘，把辉光集中在静态背景和关键控件。仅在测量有收益时调整图层，禁止全站滥用 `will-change`；继续尊重减少动态效果设置。

### P2-04 区分界面卡顿与生成等待

句子翻译在 `ZhEnAssistant.tsx:109` 等完整 JSON 返回才显示结果；实时补全在 `useRealtimeTranslation.ts:649` 消费流，但等流结束才更新最终词条。这是可见反馈偏晚的实现事实，未测真实模型耗时。不能声称换布局会提升译文质量或模型速度。

短请求只保留轻量状态；长请求允许继续输入/切换任务，并清晰保留对应原文。若增加分段预览，最终结构校验、公共入库、个人保存和贡献回执仍独立执行；预览不等于保存成功。增加取消、请求身份、旧结果防覆盖和恢复能力时必须联动后端，而非仅隐藏加载图标。

## 7. 桌面视觉层级迭代

用户认为上一轮桌面布局仍缺少设计感。本轮在现有布局上统一视觉结构，交付对象仍是实际项目，不另建脱离业务的展示原型。
