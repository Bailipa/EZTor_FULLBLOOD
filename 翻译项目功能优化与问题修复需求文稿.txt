1. 项目概述
================================================================================

1.1 项目背景
    本项目为一个英语词典翻译系统，支持批量单词/词组输入，通过大模型（LLM）
    和缓存机制提供翻译解析服务。系统包含登录用户面板和游客面板两种使用模式。

1.2 核心功能
    - 批量单词/词组输入与解析
    - 大模型（LLM）实时翻译
    - 数据库缓存命中机制
    - 公共词库共享机制
    - 非英语输入检测与拦截
    - 句子输入检测与拦截
    - 敏感词/风控词处理
    - 飞行动画效果展示

1.3 技术架构
    - 前端：Next.js + React + Framer Motion
    - 后端：Next.js API Routes + Prisma ORM
    - 数据库：Prisma（支持多种数据库）
    - 大模型：通过LLM池（llmPool）进行故障转移的流式调用

2. 问题清单与详细分析
================================================================================

2.1 问题1：非英语输入处理异常
    -------------------------------------------------------------------------
    现象：
      用户输入中文词汇"小学"，系统返回"n.[C]小学"，错误地为中文词汇添加
      英文词性标签。

    根本原因：
      (a) 系统提示词（System Prompt）中存在矛盾指令（英语词典助手 vs 文本
          翻译处理）
      (b) 缺乏语言检测机制，非英语输入被错误传递给大模型
      (c) 输入验证不足，调用大模型前无语言校验
      (d) 错误处理不当，对非英语输入无清晰友好的提示

    修复状态：已修复
    修复方案：在前端添加非英语检测逻辑，使用正则表达式 /[^\x00-\x7F]/ 
              检测非ASCII字符，对非英语输入返回固定提示"当前功能非英语不予翻译"

2.2 问题2：句子输入处理异常
    -------------------------------------------------------------------------
    现象：
      用户输入完整句子"what should people do to make their visit new york 
      city safe and pleasant"，系统将其作为单词存储到公共词库。

    根本原因：
      (a) 缺少输入验证，无法区分单词、词组和完整句子
      (b) 存储逻辑问题，完整句子被存入公共词库
      (c) 大模型处理问题，未明确区分单词、词组和句子
      (d) 用户体验问题，功能区分不清且缺乏引导

    修复状态：已修复
    修复方案：创建句子检测模块（sentenceDetector.ts），使用启发式规则检测
              句子，对句子输入返回固定提示"当前功能不能翻译句子，翻译句子
              请使用Translate Only"

2.3 问题3：多行输入中单行中文导致全部标记错误
    -------------------------------------------------------------------------
    现象：
      用户输入多行内容（包含中文和英文），如果某行包含中文，所有行都被
      标记为非英语错误。

      输入示例：
        你好
        hello
        this
        is
        test

      错误输出：所有5行都显示"当前功能非英语不予翻译"

      预期输出：仅"你好"显示非英语提示，其余正常解析

    根本原因：
      前端对整体输入进行语言检测，而非逐行检测。

    修复状态：已修复
    修复方案：改为逐行检测语言和句子类型，仅对非英语行和句子行返回固定
              提示，正常英语行继续发送到API解析。

2.4 问题4：React key冲突警告
    -------------------------------------------------------------------------
    现象：
      控制台报错：Encountered two children with the same key. Keys should 
      be unique.

    根本原因：
      使用单词本身作为React组件的key，当输入重复单词时导致key冲突。

    修复状态：已修复
    修复方案：
      - ResultsList.tsx：key从 item.word 改为 ${index}-${item.word}
      - WordInputCard.tsx：key从 word 改为 ${index}-${word}
      - GuestWordInputCard.tsx：同上

2.5 问题5：重复输入导致重复输出
    -------------------------------------------------------------------------
    现象：
      输入三个"react"，输出显示三个"react"的解析结果。

    根本原因：
      未对结果进行去重处理。

    修复状态：已修复
    修复方案：使用Map数据结构对结果进行去重，确保每个单词只出现一次。

2.6 问题6：querySelector选择器无效
    -------------------------------------------------------------------------
    现象：
      输入三个"baby"后报错：Failed to execute 'querySelector' on 
      'Document': '[data-word=""baby","baby","baby""]' is not a valid 
      selector.

    根本原因：
      (a) API返回的word字段可能变成数组形式
      (b) 构建querySelector时未正确处理引号转义

    修复状态：已修复
    修复方案：
      (a) API路由中添加类型检查，确保word字段始终为字符串
      (b) 构建querySelector时添加引号转义处理

2.7 问题7：多余"中断"提示
    -------------------------------------------------------------------------
    现象：
      输入混合内容时，已在前端处理过的非英语单词和句子也被标记为missingWords，
      显示多余的"中断"提示。

    根本原因：
      检查missingWords时使用了原始words数组，而非过滤后的normalWords数组。

    修复状态：已修复
    修复方案：将missingWords的检查范围从words改为normalWords，仅检查实际
              发送到API的正常英语单词。

2.8 问题8：Hydration failed错误
    -------------------------------------------------------------------------
    现象：
      控制台报错：Hydration failed because the server rendered text 
      didn't match the client.

    根本原因：
      HomeHeader组件中服务器端渲染"An Easier Translator"，客户端渲染
      "支持批量输入，自动结构化解析并永久保存。"，文本不一致。

    修复状态：已修复
    修复方案：统一服务器端和客户端渲染的文本内容。

2.9 问题9：输出顺序与输入顺序不一致（核心未解决问题）
    -------------------------------------------------------------------------
    现象：
      当查询内容同时包含大模型查询和缓存命中时，输出过程不按照输入顺序
      执行。虽然最终结果会按照输入顺序排序，但在执行过程中（动画、逐个
      显示）仍然不是按照输入顺序进行的。

      输入示例：
        hello     （缓存命中）
        this      （大模型查询）
        is        （缓存命中）
        a         （大模型查询）
        test      （缓存命中）
        exam      （大模型查询）

      实际执行顺序：hello → is → test → this → a → exam
      预期执行顺序：hello → this → is → a → test → exam

    根本原因分析：详见第4节

    修复状态：未完全修复
    已尝试修复：详见第3节

4. 未解决问题深度分析
================================================================================

4.1 问题本质：流式架构的时序限制
    -------------------------------------------------------------------------
    当前系统的流式数据流如下：

      后端                                前端
      ----                                ----
      缓存结果（完整JSON块）  ──────→  立即处理并显示
                                          ↓
      大模型结果（流式JSON块） ──────→  逐步处理并显示

    时序分析：

      T0: 缓存结果到达 {hello, is, test}
      T1: 前端处理 hello（第1个单词）→ 显示动画 → 添加到结果列表
      T2: 前端处理 is   （第3个单词）→ 显示动画 → 添加到结果列表
      T3: 前端处理 test （第5个单词）→ 显示动画 → 添加到结果列表
      T4: 大模型结果到达 {this, a, exam}
      T5: 前端处理 this （第2个单词）→ 显示动画 → 插入到结果列表
      T6: 前端处理 a    （第4个单词）→ 显示动画 → 插入到结果列表
      T7: 前端处理 exam （第6个单词）→ 显示动画 → 插入到结果列表

    用户看到的视觉效果：
      先显示 hello, is, test（跳过了第2、4个位置）
      然后在中间插入 this, a, exam
      最终结果正确排序，但过程混乱

4.2 当前排序方案的局限性
    -------------------------------------------------------------------------
    (a) 排序只能修复最终结果：每次 setResults 后排序只能确保最终显示的
        结果顺序正确，但无法控制动画和处理过程的顺序。

    (b) 流式架构的限制：在流式架构下，缓存结果和大模型结果的到达时间
        不同，无法在前端简单地通过排序来解决这个问题。

    (c) 缺少全局队列机制：当前实现没有全局的结果队列，无法按照输入顺序
        依次处理所有结果。

    (d) animatedWordsRef的限制：该Ref用于跟踪已处理过的单词，防止重复
        处理，但不能控制处理顺序。

4.3 影响范围
    -------------------------------------------------------------------------
    (a) 登录用户面板：当查询混合缓存命中和大模型查询时，执行过程顺序混乱
    (b) 游客面板：公共词库查询结果的显示顺序可能不一致
    (c) 用户体验：动画效果与预期不符，造成困惑

5. 推荐解决方案
================================================================================

5.1 方案1：全局结果队列（推荐）
    -------------------------------------------------------------------------
    核心思路：
      创建一个全局的结果队列，按照输入顺序依次处理所有结果。当结果到达
      时，不立即显示，而是放入队列。按照输入顺序依次从队列中取出结果
      并显示。如果某个位置的结果还未到达，等待该结果到达后再显示。

    实现要点：
      (a) 创建结果队列数据结构：
          - 每个队列项包含：word（单词）、status（等待中/已到达/已显示）、
            result（结果数据）
          - 按照输入顺序初始化队列

      (b) 结果到达处理：
          - 缓存结果到达时，标记对应队列项为"已到达"
          - 大模型结果到达时，标记对应队列项为"已到达"

      (c) 队列消费逻辑：
          - 从队列头部开始检查
          - 如果当前项状态为"已到达"且前一项已显示，则处理并显示当前项
          - 如果当前项状态为"等待中"，则暂停处理，等待结果到达

      (d) 动画控制：
          - 仅在队列消费时触发动画
          - 确保动画按照输入顺序执行

    伪代码：

      // 初始化队列
      const queue = words.map(word => ({
        word,
        status: 'pending',  // pending | arrived | displayed
        result: null
      }));

      // 结果到达回调
      function onResultArrived(word, result) {
        const item = queue.find(q => q.word === word);
        if (item) {
          item.status = 'arrived';
          item.result = result;
          processQueue();  // 尝试处理队列
        }
      }

      // 队列处理
      async function processQueue() {
        for (const item of queue) {
          if (item.status === 'displayed') continue;
          if (item.status === 'pending') break;  // 等待结果到达
          if (item.status === 'arrived') {
            await showAnimation(item.result);  // 显示动画
            await addToResults(item.result);   // 添加到结果列表
            item.status = 'displayed';
          }
        }
      }

    优点：
      - 完全按照输入顺序显示
      - 动画效果也按照输入顺序执行
      - 用户体验最佳

    缺点：
      - 实现复杂度较高
      - 需要修改前端处理逻辑
      - 可能增加等待时间（如果前面的单词需要大模型查询，后面的缓存
        结果也需要等待）

5.2 方案2：分批发送结果
    -------------------------------------------------------------------------
    核心思路：
      修改后端，将缓存结果和大模型结果分批发送，每批按照输入顺序排列。

    实现要点：
      (a) 后端先发送第一批结果（包含所有缓存命中的单词），按照输入顺序
      (b) 前端收到第一批结果后，按照输入顺序显示
      (c) 后端继续处理大模型查询，每完成一个就发送一个结果
      (d) 前端收到大模型结果后，插入到正确的位置

    优点：
      - 实现相对简单
      - 缓存结果可以立即显示

    缺点：
      - 仍然可能出现顺序问题
      - 需要修改后端的流式处理逻辑

5.3 方案3：延迟显示
    -------------------------------------------------------------------------
    核心思路：
      前端收到所有结果后，延迟一段时间再按照输入顺序显示。

    实现要点：
      (a) 前端收到缓存结果后，不立即显示
      (b) 等待所有大模型结果到达后，按照输入顺序一次性显示所有结果

    优点：
      - 实现简单
      - 完全按照输入顺序显示

    缺点：
      - 用户体验差，需要等待所有结果到达
      - 失去了流式显示的优势
      - 对于大量单词的查询，等待时间可能很长

5.4 方案对比
    -------------------------------------------------------------------------
    ┌──────────┬────────────┬────────────┬────────────┬────────────┐
    │  方案    │  顺序保证  │  实现复杂度│  用户体验  │  等待时间  │
    ├──────────┼────────────┼────────────┼────────────┼────────────┤
    │ 方案1    │  完全保证  │  高        │  最佳      │  适中      │
    │ 方案2    │  部分保证  │  中        │  较好      │  较短      │
    │ 方案3    │  完全保证  │  低        │  最差      │  最长      │
    └──────────┴────────────┴────────────┴────────────┴────────────┘

    综合评估：推荐方案1（全局结果队列），虽然实现复杂度较高，但能完全
    保证顺序，且用户体验最佳。

6. 大小写一致性规范
================================================================================

6.1 规则定义
    -------------------------------------------------------------------------
    规则1：保留所有必须大写的特殊情况
      - 首字母缩写词：AI, API, CSS, HTML, HTTP, HTTPS, JSON, JS, TS, 
        UI, UX 等
      - 驼峰命名法的专有名词：JavaScript, TypeScript, React, Next.js, 
        Node.js 等
      - 品牌名称：Google, Microsoft, Apple, Amazon, Facebook, Twitter, 
        GitHub 等
      - 其他约定俗成需要大写的特殊词汇

    规则2：除上述特殊情况外，统一转换为小写字母格式
      - 普通单词：apple, banana, hello, world 等
      - 词组：green apple, take for granted 等

6.2 实现方式
    -------------------------------------------------------------------------
    函数：normalizeCase(text: string): string

    逻辑：
      (a) 检查是否匹配特殊情况的字符串（精确匹配）
      (b) 检查是否匹配特殊情况的正则表达式（模式匹配）
          - /^[A-Z0-9]+$/ ：全大写的缩写词
          - /^[A-Z][a-z]+(?:[A-Z][a-z]+)*$/ ：驼峰命名法
      (c) 如果匹配特殊情况，保留原始大小写
      (d) 如果不匹配，转换为小写

6.3 特殊情况维护
    -------------------------------------------------------------------------
    当前特殊情况列表需要持续维护，建议：
      (a) 将特殊情况列表提取为配置文件或数据库表
      (b) 支持动态添加和删除特殊情况
      (c) 定期审查和更新列表

7. 测试验证标准
================================================================================

7.1 非英语输入测试
    -------------------------------------------------------------------------
    测试用例：
      输入：你好
      预期输出：非英语 / 当前功能非英语不予翻译

      输入：hello
      预期输出：正常解析结果

      输入（多行混合）：
        你好
        hello
        this
      预期输出：
        你好 → 非英语 / 当前功能非英语不予翻译
        hello → 正常解析结果
        this → 正常解析结果

7.2 句子输入测试

8. 技术约束与注意事项
================================================================================

8.1 依赖约束
    -------------------------------------------------------------------------
    (a) 大模型要求：确保大模型能准确检测语言，语言检测准确率需达到95%以上
    (b) 性能要求：语言检测必须高效，不能显著增加响应时间
    (c) 兼容性要求：修改必须兼容现有API格式，确保向后兼容

8.2 系统约束
    -------------------------------------------------------------------------
    (a) 兼容性：修改必须兼容现有API格式
    (b) 向后兼容：确保现有功能不受影响
    (c) 可扩展性：设计应考虑未来语言支持扩展
    (d) Translate Only功能：所有修改不得影响Translate Only功能的正常使用

8.3 安全约束
    -------------------------------------------------------------------------
    (a) 输入验证：所有输入必须严格验证
    (b) 错误处理：系统信息不得在错误消息中泄露
    (c) 速率限制：维持现有速率限制机制
    (d) 一致性：错误处理必须与敏感词机制一致

8.4 性能约束
    -------------------------------------------------------------------------
    (a) 流式响应：保持流式响应的特性，不能改为同步等待
    (b) 缓存利用：充分利用缓存机制，减少大模型调用
    (c) 动画流畅：确保动画效果流畅，不卡顿
    (d) 内存占用：全局结果队列的内存占用需控制在合理范围内

8.5 代码质量约束
    -------------------------------------------------------------------------
    (a) 代码风格：遵循现有代码风格和命名规范
    (b) 注释：不添加不必要的注释（除非用户要求）
    (c) 类型安全：确保TypeScript类型安全
    (d) 错误处理：完善的错误处理和边界情况处理
